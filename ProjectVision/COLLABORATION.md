# AgentRouter — 多 Agent 协同模型

> **五个核心维度：任务分解 · Agent 指派 · 任务回收 · PM 拆解质量 · 多 Agent 协同**

---

## 核心命题

多 Agent 协同不是简单地把任务扔给多个 CLI 各自执行。真正的挑战在于：

```
一个需求 → 拆成多个任务 → 分给不同 Agent → 各自干活 → 结果汇合
                                               ↑
                                         这里藏着所有难题
```

**AgentRouter 要突破的五个维度：**

```
┌──────────────────────────────────────────────────┐
│                  协同模型                          │
├──────────┬──────────┬──────────┬──────────┬───────┤
│ 任务分解  │ Agent指派│ 任务回收  │ PM拆解   │ 多Agent │
│ 拆得刚好  │ 知人善任  │ 干完交接  │ 质量保障  │ 接力赛  │
└──────────┴──────────┴──────────┴──────────┴───────┘
```

---

## 维度一：任务分解（Task Decomposition）

### 问题

PM 拆任务时，粒度是成败的关键：

```
太粗 ❌ → "重构整个项目"
          一个 Agent 干不完，没有其他 Agent 能并行
          等于没拆

太细 ❌ → "把第 3 行空格改成 tab"
          调度成本 > 执行收益
          拆了不如不拆

刚好 ✅ → "提取用户认证模块为独立 service"
          边界清晰、可独立执行
          依赖明确、可并行
```

### 分解原则

| 原则 | 说明 |
|---|---|
| **独立可执行** | 每个任务不依赖执行中的其他任务（依赖只存在于任务间） |
| **边界清晰** | 有明确的文件/模块范围（`path` 字段） |
| **可验证** | 执行完成后能明确判断"做完了" |
| **避免过细** | 单任务执行时间 > 调度开销的 10 倍 |

### 任务结构

```
{
  id: "t1",
  title: "数据库：添加 roles 和 permissions 表",
  assignee: "codewhale",
  path: "./src/models/",
  depends_on: [],                    // 前置依赖
  output_contract: {                 // 产出契约
    files: ["./src/models/role.ts", "./src/models/permission.ts"],
    type: "create"                   // create | modify | delete | review
  }
}
```

`output_contract` 是关键字段——它告诉平台和下游 Agent：**这个任务干完后会留下什么**。

## 维度二：Agent 指派（Agent Assignment）

### 问题

不是所有 Agent 都适合所有任务。指派错误会导致：

```
让 Reasonix 写代码     → 推理强但编码慢
让 CodeWhale 做审查    → 编码快但规划弱
让一个 Agent 干所有事  → 失去"多 Agent"的意义
```

### 能力模型

每个 Agent 注册时声明自己的能力标签：

```typescript
interface AgentCapability {
  name: string;           // ar-codewhale
  roles: Role[];          // ["coder", "reviewer"]
  strengths: string[];    // ["code-generation", "refactoring"]
  weaknesses: string[];   // ["architecture-design", "security-audit"]
  costPerTask: number;    // 相对成本
}
```

### 指派策略

| 策略 | 行为 | 适合 |
|---|---|---|
| **精确指派** | PM 直接指定 assignee | 需求明确 |
| **自动匹配** | 调度器按能力标签匹配 | 多 Agent 可选 |
| **回退指派** | 首选 Agent 失败时自动换人 | 高可用场景 |

### 指派示例

```
PM 拆解结果：
  t1 "添加数据库表"     → strengths: ["code-generation"]  → CodeWhale
  t2 "做安全审查"       → strengths: ["security-audit"]    → Reasonix
  t3 "写 API 文档"      → strengths: ["documentation"]     → CodeWhale
```

## 维度三：任务回收（Task Handover）

### 问题

**这是多 Agent 协同的核心痛点。** 主人举的例子一针见血：

> 一个脚本文件，A 改完了，B 怎么接着干？

```
A 改完脚本
    │
    ├── B 要知道 A 改了啥？         → 增量信息
    ├── B 要全量读取还是只看变更？   → 读取模式
    ├── A 改出 bug 怎么办？         → 质量反馈
    └── A 和 B 能同时改一个文件吗？  → 冲突处理
```

### 三级回收模型

#### Level 1：文件级 Diff（基础）

```
A 执行完成 → 产出变更清单
  → 修改了：src/auth/login.ts（+15 -3 行）
  → 新增了：src/auth/refresh.ts（+42 行）
  → 删除了：src/auth/old_login.ts（-30 行）

B 拿到后 → 只读增量，知道从哪开始
```

**适用**：任务间有清晰的文件边界

#### Level 2：上下文摘要（标准）

```
A 执行完成 → 产出自然语言摘要

"我把 auth 模块从 login.ts 中抽离成独立 service：
  - 新增 src/auth/login.ts → login/logout 接口
  - 新增 src/auth/refresh.ts → token 刷新逻辑
  - 修改 src/auth/index.ts → 注册新路由
  - 数据库新增 refresh_tokens 表
  
  待办：下一步需要加 JWT 密钥轮换"
```

B 拿到后 → 不用读代码就知道上下文

**适用**：任务间有逻辑依赖

#### Level 3：检查点（高级）

```
A 执行完成 → 产出完整检查点

{
  checkpoint: {
    state: "auth_service_baseline_v1",
    files_changed: [...],
    coverage: { lines: 87%, branches: 72% },
    known_issues: [
      "refresh token 未设过期时间",
      "缺少 rate limiting"
    ],
    next_steps: [
      "加 JWT 密钥轮换",
      "加登录失败锁定"
    ],
    artifacts: {
      design_doc: "./docs/auth-design.md",
      test_report: "./test/auth-test.log"
    }
  }
}
```

B 拿到后 → 完全了解当前状态，直接开始下一阶段

**适用**：复杂多阶段任务

### 回收流程

```
任务 A 完成
    │
    ├── 产出变更文件（实际代码改动）
    ├── 产出回收包（Diff / 摘要 / 检查点）
    │
    ▼
平台记录回收包 → 写入 events/ + 数据库
    │
    ▼
调度器检查任务 B 的 depends_on
    │
    ├── 如果 B 依赖 A → 注入回收包到 B 的上下文
    │
    ▼
任务 B 启动 → 读取回收包 → 在 A 的基础上继续
```

## 维度四：PM 拆解质量（PM Decomposition Quality）

### 问题

PM 拆得好不好，直接决定整个执行链路的成败：

```
拆得好 → 任务清晰 → 执行顺畅 → 一次通过
拆不好 → 任务模糊 → 反复修改 → 不如不拆
```

### 影响拆解质量的因素

| 因素 | 当前 | 目标 |
|---|---|---|
| **项目理解** | PM 只看用户需求 | PM 先读项目结构 + 现有代码 |
| **历史记忆** | 每次从零开始 | 记住上次踩的坑 |
| **自我审查** | 拆完直接提交 | 拆完后自己 Review 一遍 |
| **用户反馈** | 无反馈闭环 | 用户可修改任务列表 |

### 质量提升路径

#### 第一步：知情拆解

PM 在拆任务前，先做三件事：

```
1. 读项目结构
   → ls 项目根目录 → 了解模块划分

2. 读关键文件
   → package.json / Cargo.toml → 知道技术栈
   → 现有路由文件 → 知道代码风格

3. 读相关模块
   → 跟需求相关的现有代码 → 避免重复
```

#### 第二步：自我审查

PM 拆完后，自己审查一遍：

```
审查清单：
  ☐ 每个任务有明确的 assignee？
  ☐ 每个任务有文件路径范围？
  ☐ 依赖关系是否正确？
  ☐ 并行组是否合理？
  ☐ 有没有遗漏的任务？
  ☐ 有没有不必要的任务？
```

#### 第三步：用户反馈闭环

```
用户看到任务列表
    │
    ├── 满意 → 确认执行
    │
    ├── 修改 → 调整任务后重新提交
    │
    └── 不满意 → 对话追问 → PM 重新拆解
```

#### 第四步：记忆增强

PM 记住历史模式：

```
项目 A 上次拆解时：
  - 数据库迁移任务容易被遗漏 → 下次主动补上
  - 测试任务粒度太粗 → 下次拆细
  - 用户喜欢 YOLO 模式 → 默认用 YOLO
```

## 维度五：多 Agent 协同（Multi-Agent Collaboration）

### 核心模型：文件即契约

主人说的脚本场景就是最纯粹的形式——

**文件是多 Agent 之间默认的通信协议。**

```
Agent A（CodeWhale）
  → 修改 auth.py
  → 文件变更
      ↓
平台检测到 auth.py 的变更
  → 记录 diff
  → 触发依赖任务
      ↓
Agent B（Reasonix）
  → 读取最新 auth.py
  → 做 Code Review
  → 产出审查报告
      ↓
Agent A（CodeWhale）再次
  → 按审查报告修改
  → 循环直到通过
```

### 三种协同模式

#### 模式 A：接力赛（Pipeline）

```
t1 → CodeWhale（写代码）
  ↓ 文件变更 + 回收包
t2 → Reasonix（审查）
  ↓ 审查报告
t3 → CodeWhale（修问题）
  ↓
完成
```

**特点**：串行、依赖明确、适合有质量门槛的流程

#### 模式 B：并行赛（Parallel）

```
      t2 → CodeWhale（写 API 文档）
t1 ── t3 → CodeWhale（写单元测试）
      t4 → Reasonix（做安全审查）

t1（建数据库表）完成后，t2/t3/t4 同时启动
```

**特点**：并行、互不依赖、适合独立模块

#### 模式 C：迭代赛（Iterative）

```
t1 → CodeWhale（写代码）
  ↓ 审查结果
t2 → CodeWhale（修改）
  ↓ 审查结果
t3 → CodeWhale（再修改）
  ↓ 通过
完成
```

**特点**：循环、质量逐步提升、适合需要打磨的任务

### 文件变更驱动的协同流程

```
平台维护一个文件变更日志：

事件: file:modified  path: src/auth/login.ts  agent: codewhale
事件: file:created   path: src/auth/refresh.ts  agent: codewhale
事件: file:deleted   path: src/auth/old_login.ts  agent: codewhale
```

当下游 Agent 启动时：

```
Agent B 启动
  → 查询文件变更日志（自任务 A 以来的变更）
  → 读取变更后的文件最新版本
  → 在 A 的基础上继续工作
  → 不会读到 A 修改前的旧版本
```

### 冲突处理

| 场景 | 处理方式 |
|---|---|
| **两个 Agent 改同一个文件** | 按依赖顺序串行，或 PM 拆解时避免 |
| **Agent B 发现 Agent A 的 bug** | B 直接修，或在审查报告中标记，由调度器决定 |
| **Agent A 执行失败** | 调度器尝试重新指派，或通知用户 |

## 总结

| 维度 | 核心问题 | 答案 |
|---|---|---|
| **任务分解** | 拆多细？ | 独立可执行，调度成本 < 10% 执行成本 |
| **Agent 指派** | 谁来做？ | 按能力标签匹配，知人善任 |
| **任务回收** | 干完怎么交接？ | 三级模型：Diff → 摘要 → 检查点 |
| **PM 拆解质量** | 怎么拆得准？ | 知情拆解 + 自我审查 + 反馈闭环 + 记忆增强 |
| **多 Agent 协同** | 怎么配合？ | 文件即契约，三种模式：接力 / 并行 / 迭代 |

> **AgentRouter 不是让多个 Agent 一起干活，而是让多个 Agent 有序地一起干活。**
