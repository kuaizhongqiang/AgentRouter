# AgentRouter — 系统架构

> **整合：协同模型 · 标签系统 · 执行模型 · 上下文预算**

---

## 顶层架构

```
┌────────────────────────────────────────────────────────┐
│                    AgentRouter                          │
│               「多开源 CLI 编程助手调度器」              │
├────────────────────────────────────────────────────────┤
│                                                        │
│  ┌─────────┐  ┌──────────┐  ┌──────────┐  ┌────────┐ │
│  │  调度器  │  │ Agent    │  │ 通信协议  │  │ 数据层  │ │
│  │(Scheduler)│  │ 适配器   │  │(Protocol) │  │(SQLite)│ │
│  └────┬────┘  └────┬─────┘  └─────┬────┘  └───┬────┘ │
│       │            │              │            │       │
│       └────────────┴──────────────┴────────────┘       │
│                       ↓                                │
│            ┌────────────────────┐                      │
│            │    UI (Vue 3)      │                      │
│            └────────────────────┘                      │
└────────────────────────────────────────────────────────┘
```

### 职责边界

| 模块 | 做 | 不做 |
|---|---|---|
| **调度器** | 谁来做、什么时候做、怎么做 | 不读代码、不改文件、不改任务 |
| **Agent 适配器** | 翻译平台指令↔CLI 参数 | 不侵入 CLI 内部逻辑 |
| **通信协议** | 定义消息格式、事件流 | 不定义业务逻辑 |
| **数据层** | 持久化对话、任务、日志 | 不存储代码 |

## 协同模型（5个维度）

### 维度一：任务分解

拆到**独立可执行**的粒度：

```
太粗 ❌ → "重构整个项目"（一个Agent干不完）
太细 ❌ → "把第3行空格改成tab"（调度成本 > 执行收益）
刚好 ✅ → "提取用户认证模块为独立service"（边界清晰、依赖明确）
```

| 原则 | 说明 |
|---|---|
| **独立可执行** | 不依赖执行中的其他任务 |
| **边界清晰** | 有明确的文件/模块范围 |
| **可验证** | 执行完成后能判断"做完了" |
| **避免过细** | 单任务执行时间 > 调度开销 10 倍 |

### 维度二：Agent 指派

根据标签系统匹配任务和 Agent（详见下方标签系统）。

两步决策：
1. **派给谁** — 按 `best_for` / `not_for` 匹配能力
2. **派几个** — 按 `execution_model.max_instances` 决定并行度

### 维度三：任务回收

A 干完了，B 怎么接？三级回收模型：

| 级别 | 内容 | 适合 |
|---|---|---|
| **Level 1: Diff** | 变更文件 + 行数统计 | 文件边界清晰 |
| **Level 2: 摘要** | 自然语言描述改动内容 | 有逻辑依赖 |
| **Level 3: 检查点** | 完整状态 + 待办 + 已知问题 | 复杂多阶段 |

回收包通过 metadata.context.deltas 传递。

### 维度四：PM 拆解质量

| 提升路径 | 做法 |
|---|---|
| **知情拆解** | PM 先读项目结构 + 关键文件，再拆 |
| **自我审查** | 拆完后审查清单过一遍 |
| **反馈闭环** | 用户可修改任务列表 |
| **记忆增强** | 记住历史模式，下次更准 |

### 维度五：多 Agent 协同

三种协同模式：

```
接力赛（Pipeline）  并行赛（Parallel）  迭代赛（Iterative）
t1→t2→t3           t1    t2          t1→t2→t3→t4
                    t3    t4          不断循环打磨
串行                并行              循环
```

**核心模型：文件即契约。** 文件变更是 Agent 之间默认的通信协议。

### 维度六：动态调整

任务不是一次拆完就固定的。执行中 Agent 可向 PM 提建议，PM 动态调整。

#### 调整流程

```
A 执行中发现："如果 B 在 beta 中加配置层会更科学"
  → A 通过 suggestion 事件向 PM 提建议
  → 平台检查 PM 进程：
      ├── PM 还在 → 转发建议
      └── PM 已退 → 重新 spawn PM，注入当前上下文
  → PM 评估建议
  → PM 决策并发出调整事件
```

#### PM 决策矩阵

| B 的状态 | PM 决策 |
|---|---|
| 还没开始 | 直接修改 t2 的任务描述 |
| 已开始，不冲突 | 追加补充任务 t2b |
| 已开始，冲突 | 标记冲突，完成后人工介入 |
| 已完成 | 追加新任务，或忽略 |

#### 调整事件

| 事件 | 发送者 | 含义 |
|---|---|---|
| `suggestion` | 执行中的 Agent | 向 PM 提建议 |
| `task:update` | PM | 修改已有任务 |
| `task:add` | PM | 追加新任务 |
| `task:cancel` | PM | 取消任务 |

**原则：PM 是唯一决策者，Agent 只能提建议。**

#### 与标签系统的关系

Agent 的标签可以声明是否具备提建议的能力：

```json
{
  "capabilities": {
    "can_suggest": true,
    "suggestion_scope": "related_tasks"  // own_task | related_tasks | all
  }
}
```

### 三种并行模式

| 模式 | 代表 | max_instances | PM 拆解策略 |
|---|---|---|---|
| **sub-agent** 🧩 | Reasonix | 1 | 只拆 1 个，内部子任务自己并行 |
| **multi-process** 🚀 | CodeWhale | 4 | 可拆多个并行，不超上限 |
| **single** 🐌 | 轻量 CLI | 1 | 只能串行，需排队 |

## 执行模型

### 进程级并行

每个 `spawn()` 是独立 OS 进程：

```
AgentManager
  ├── spawn('ar-codewhale', task1) → PID 1001
  ├── spawn('ar-codewhale', task2) → PID 1002
  ├── spawn('ar-reasonix', task3)  → PID 1003
  └── Map<taskId, ChildProcess> 统一管理
```

进程管理：SIGTERM → 5秒超时 → SIGKILL，避免孤儿进程。

### 资源建议

| 任务类型 | 建议并行数 |
|---|---|
| 轻量（改配置、简单函数） | 4-6 个 |
| 中等（加模块、重构函数） | 2-3 个 |
| 重量（大规模重构、全量审查） | 串行或最多 2 个 |

### 文件冲突

| 方案 | 做法 | 代价 |
|---|---|---|
| **PM 规划时避免** | 拆任务时确保文件不重叠 | 依赖 PM 质量 |
| **串行兜底** | 检测到文件重叠时自动串行 | 损失并行效率 |

## 上下文预算

### 三种读取模式

| 模式 | 读取范围 | Token 效率 | 适用 |
|---|---|---|---|
| **全量** 🏋️ | 整个文件 | 低 | 任务读不同文件 |
| **增量** 📊 | Diff + 相关上下文 | 高（省 90%） | 接力、审查 |
| **差异** 🔍 | 最终状态 | 最高 | 迭代改同一文件 |

### 经济账

```
1000 行脚本，拆 3 个任务

❌ 无上下文传递（每个都读全量）
  t1: 1000 → t2: 1000 → t3: 1000 = 3000 Token
  有效：1000 | 浪费：2000（67%）

✅ 有上下文传递（增量读取）
  t1: 1000 → t2: 50 → t3: 30 = 1080 Token
  有效：1080 | 浪费：0

节省 64%
```

### PM 的粒度策略

| 场景 | 策略 | 理由 |
|---|---|---|
| 多个独立文件 | 按文件边界拆 | 简单、并行、无重复 |
| 单文件多轮修改 | 按变更链路拆 | 增量传递省 Token |
| 模块内多子任务 | 按模块切分 | 并行 + 增量兼顾 |

## 架构全景图

```
用户输入需求
    │
    ▼
┌──────────────┐
│   调度器路由   │ ← 查标签库，选 PM Agent
│  · 查 best_for │
│  · 查 max_inst │
└──────┬───────┘
       │ spawn
       ▼
┌──────────────┐
│  PM Agent     │ → 知情拆解 → 自我审查 → 产出任务列表
│  (Reasonix)   │    每个任务带 output_contract
└──────┬───────┘
       │ 返回任务列表
       ▼
┌──────────────┐
│   调度器       │ → 按 parallel_groups 调度
│  · 能力匹配   │    组内并行，组间串行
│  · 并行度控制 │    注入上下文（scope + deltas）
│  · 上下文注入 │
└──────┬───────┘
       │ spawn
       ▼
┌──────────────┐
│  并行执行组    │
│  t1 → Agent A │ → stdout 事件流 → events/ .jsonl
│  t2 → Agent B │ → metadata 标记上下文
│  t3 → Agent C │ → 产出回收包
└──────┬───────┘
       │ 回收
       ▼
┌──────────────┐
│  下一组 / 汇总 │ → 结果汇聚到 UI
└──────────────┘
```
